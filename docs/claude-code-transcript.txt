## RequestLog: the memory for the 100-per-60-seconds rule

To enforce "no more than 100 requests in any rolling 60-second window", the service has to remember when each recent request arrived. `RequestLog` is that memory. It has one row per accepted request: which supplier, and at what time.

On each incoming request for supplier X:
1. Count the rows for X with `RequestedAtMs` within the last 60 seconds.
2. If the count is 100 or more, reject the request with 429 and don't add a row.
3. Otherwise, add a row and continue with the ingest.

The window slides on its own as time passes. A request logged 61 seconds ago simply stops being counted, and old rows can be deleted.

I'd store this in the database rather than in memory because the brief says the service runs on multiple server instances. An in-memory counter would give each instance its own limit, so a supplier could send 100 requests to each of three instances. A shared table makes the limit global.

## SupplierStats: the totals for the stats endpoint

`GET /stats/{supplierId}` must report how many reservations were ingested and how many requests were throttled. Throttled requests are rejected before anything is saved, so no other table records them. We need a place to keep that number, and that's `SupplierStats`. It has one row per supplier, with counters:
- `IngestedCount` goes up when a reservation is created or updated.
- `UnchangedCount` goes up on an exact duplicate (an extra, not required by the spec).
- `ThrottledCount` goes up on each 429.

The stats endpoint then reads a single row.

## Why two tables

They serve different purposes:
- `RequestLog` is temporary and short-lived. It only matters for the last 60 seconds and gets pruned.
- `SupplierStats` is permanent and cumulative, and it only grows.

We could use one table for both. If we kept every request forever, with an outcome column, we could compute both the window count and the stats from it. That's simpler on the schema, but the table would grow without bound and the stats queries would get slower over time. Two small tables avoid that.

[ASSISTANT] ## Service design

**Repository pattern: yes, but with some adjustments.**

- **No DbContext.** That's an Entity Framework concept. With Dapper, the equivalent is an `IDbConnectionFactory` that opens SQLite connections.
- **Repositories:** `IReservationRepository`, `IRequestLogRepository` and `ISupplierStatsRepository`. Each owns the SQL for its table, and controllers never touch them directly.
- **One shared transaction.** The throttle check, the reservation upsert and the stats update must happen atomically, or concurrent requests can slip past the limit. So the repositories take an `IDbTransaction`, and a small `IUnitOfWork` (or transaction scope) creates the connection and transaction and passes it to them.
- **Services hold the logic.** The controllers stay thin, and the services hold the business rules:
  - `IReservationIngestService`: dedup, update and stale rules.
  - `IThrottleService`: the rolling window.
  - `IStatsService`: reads the counters.
- **Flow:** controller → service → repositories → SQLite, wired with DI. Request DTOs are separate from the DB entities.
- **Time:** an `IClock` abstraction, so tests can control time. Without it, the throttle can't be tested reliably.

/// <summary>
/// Persistence operations for the <c>RequestLog</c> table, the record of recent accepted requests
/// used to enforce the rolling throttle window. Timestamps are Unix milliseconds (UTC).
/// </summary>
public interface IRequestLogRepository
{
    /// <summary>
    /// Counts a supplier's logged requests strictly after the given instant.
    /// </summary>
    /// <param name="supplierId">The supplier.</param>
    /// <param name="afterUnixMs">Exclusive lower bound, in Unix milliseconds.</param>
    /// <param name="cancellationToken">Cancels the operation.</param>
    /// <returns>The number of matching requests.</returns>
    Task<int> CountAfterAsync(string supplierId, long afterUnixMs, CancellationToken cancellationToken);

    /// <summary>
    /// Gets the earliest logged request strictly after the given instant.
    /// </summary>
    /// <param name="supplierId">The supplier.</param>
    /// <param name="afterUnixMs">Exclusive lower bound, in Unix milliseconds.</param>
    /// <param name="cancellationToken">Cancels the operation.</param>
    /// <returns>The earliest timestamp, or <see langword="null"/> if there are none.</returns>
    Task<long?> GetEarliestAfterAsync(string supplierId, long afterUnixMs, CancellationToken cancellationToken);

    /// <summary>
    /// Records an accepted request.
    /// </summary>
    /// <param name="supplierId">The supplier.</param>
    /// <param name="requestedAtUnixMs">When the request arrived, in Unix milliseconds.</param>
    /// <param name="cancellationToken">Cancels the operation.</param>
    Task AddAsync(string supplierId, long requestedAtUnixMs, CancellationToken cancellationToken);

    /// <summary>
    /// Deletes a supplier's requests at or before the given instant, keeping the table bounded.
    /// </summary>
    /// <param name="supplierId">The supplier.</param>
    /// <param name="atOrBeforeUnixMs">Inclusive upper bound, in Unix milliseconds.</param>
    /// <param name="cancellationToken">Cancels the operation.</param>
    /// <returns>The number of rows deleted.</returns>
    Task<int> DeleteAtOrBeforeAsync(string supplierId, long atOrBeforeUnixMs, CancellationToken cancellationToken);
}

Supplier Feed Throttle & Dedup Service: an ASP.NET Core Web API (.NET 8) backed by SQLite and Dapper.

## Running

```
dotnet run --project src/SupplierFeed.Api
```

Swagger UI is served at `/swagger` (the launch profile opens it automatically).

## Tests

```
dotnet test SupplierFeed.slnx
```

## Layout

- `src/SupplierFeed.Api` - the Web API (controllers, services, repositories).
- `tests/SupplierFeed.Tests` - unit and integration tests.
- `.claude/skills` - project skills (SOLID/patterns, performance, docs + tests) used during development.

## Design

Request flow: controller -> service -> repositories (Dapper) -> SQLite. Repositories are created per request by a unit of work, so the throttle check, reservation write and stats update share one transaction.

## Assumptions

- **SQLite** is the database: no install needed. Multiple server instances are only correct if they share the same database; in production this would move to SQL Server/Postgres (the SQL is kept simple for that).
- **Reservation identity** is (`supplierId`, `reservationId`): two suppliers may reuse the same reservation id.
- **Price** is stored as TEXT (exact decimal), because SQLite has no decimal type and floats are unsafe for money. Timestamps are ISO 8601 UTC TEXT.
- **Throttling state lives in the database** (`RequestLog`) rather than memory, so the limit holds across instances. Write requests take the SQLite write lock up front (`BEGIN IMMEDIATE`) so the check-then-write cannot interleave; reads do not.

  - A changed one is updated and returns `200` with `changed: true`.

**Choices I made where the spec was silent**
These are documented in the README.
- Only accepted requests count toward the limit, so retrying while throttled doesn't extend the penalty. Duplicates do count.
- "Same details" means same room, check-in, check-out and price. A resend that only changes `updatedAtUtc` counts as unchanged.
- If details differ but the incoming `updatedAtUtc` is older than the stored one, the stored data is kept (outcome `Stale`). An old retry can't overwrite newer data.
